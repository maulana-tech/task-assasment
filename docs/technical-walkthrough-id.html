withRetry

  • Retry dengan exponential backoff: 250ms → 500ms → 1s → 2s → 4s → 8s
  • Random jitter (0-100ms) untuk hindari thundering herd
  • TIDAK retry error isRangeTooLarge — itu trigger span halving

isRangeTooLarge

Pattern-matching pesan error dari berbagai provider. Cek: "more than", "too many", "range too large", "block range", "exceed", "limited to", "timeout".

src/ingest.ts 181 baris

Tujuan: Ambil block dari RPC, ekstraksi transfer, tulis ke SQLite. Tangani reorg, retry, batasan provider.

Alur ingestRange

  1. Mulai dengan chunk size (default 200), dibatasi [10, 2000]
  2. Untuk setiap chunk:
    • rpc.getTransferLogs(n, end) — event Transfer ERC-20
    • Jika "too many results" → bagi 2 chunk, retry
    • rpc.getBlock(b) untuk setiap block (parallel, concurrency=8)
    • Cek parentHash → deteksi reorg
    • Jika reorg: cari common ancestor, rollback, mulai ulang
    • Jika tidak: extractTransfers() → db.writeBlock()
  3. Log progress, kali 2 chunk size (sampai ceiling)

extractTransfers

Dua sumber transfer:

  1. Native ETH: tx.value > 0n && tx.to !== null → logIndex: -1, asset: 'ETH'
  2. ERC-20: topics.length === 3 && data.length === 66 → ekstrak from/to dari topics, amount dari data
    • Filter out: 4-topic (ERC-721), data pendek (bukan uint256)

Penanganan reorg

Jalan backward membandingkan hash tersimpan dengan hash live. Yang pertama match = common ancestor. Hapus semua di atasnya, ingest ulang.

verifyTail

Untuk follow mode: cek 12 block tersimpan terakhir setiap poll. Jika hash tidak cocok → rollback.

src/trace.ts 213 baris

Tujuan: Algoritma BFS trace dan hop terpendek. Inti dari sistem.

Tipe data

type TraceOptions = {
  depth?: number;           // max hop (default 3)
  direction?: 'down' | 'up' | 'both';
  maxNodes?: number;        // default 500
  maxEdgesPerNode?: number; // default 200
  fromBlock?: number;
  toBlock?: number;
};

type TraceResult = {
  seed: { type: 'tx' | 'address'; value: string };
  window: [number, number];
  nodes: TraceNode[];       // { address, hop, isContract }
  edges: TraceEdge[];       // Transfer + { hop, direction }
  truncated: boolean;
  truncatedAt: string[];
};

traceTx

  1. Muat seed edges via db.transfersByTx(txHash)
  2. Set posisi seed: (block, txIndex, -1)
  3. BFS downstream dari penerima
  4. BFS upstream dari pengirim
  5. finish(): bangun nodes, dedup edges

Aturan temporal

const after = (e: Transfer, p: Pos) => cmp(e, p) > 0;
const before = (e: Transfer, p: Pos) => cmp(e, p) < 0;
const cmp = (e: Transfer, p: Pos) =>
  e.blockNumber - p.block || e.txIndex - p.txIndex || e.logIndex - p.logIndex;

Membandingkan tuple (block, txIndex, logIndex). Downstream harus setelah; upstream harus sebelum.

Terminasi siklus

Setiap alamat dikunjungi sekali di hop terpendek. BFS menjamin kunjungan pertama = terpendek.

Batas fan-out

if (edges.length > o.maxEdgesPerNode) {
  edges = edges.slice(0, o.maxEdgesPerNode);
  res.truncated = true;
  res.truncatedAt.push(addr);
}

4. Alur Data

Alur Ingestion

CLI (cli.ts) → assertSepolia() // verifikasi chain ID → createChainReader() // viem client → ingestRange() // (ingest.ts) → untuk setiap chunk: rpc.getTransferLogs() // event ERC-20 rpc.getBlock() × N // header block + tx untuk setiap block: cek parentHash // deteksi reorg extractTransfers() db.writeBlock() → update cursor

Alur Query Trace

HTTP request (server.ts) → route() // parse URL + params → traceTx(db, hash, opts) // (trace.ts) → db.transfersByTx() // seed edges → bfs(db, ..., 'down') // downstream BFS → bfs(db, ..., 'up') // upstream BFS → finish() // bangun nodes, dedup edges → classify(db, rpc, result) // eth_getCode untuk yang tidak diketahui → JSON response

Alur Query Hops

HTTP request (server.ts) → route() → hops(db, from, to, opts) // (trace.ts) → BFS dari source → expand neighbor setiap hop → cek aturan temporal → return saat tujuan tercapai atau maxDepth tercapai → JSON response

5. Keputusan Desain Utama

Kenapa SQLite bukan Postgres?
Zero infrastructure — single file, sudah ada di Node. Cukup untuk tool trace single-user. WAL mode handle concurrent reads + single writer.
Kenapa hanya transfer-only edge?
Cakup ETH + ERC-20 (2 tipe yang diminta). Internal call butuh debug_traceTransaction yang tidak tersedia di public endpoint.
Kenapa BFS bukan DFS?
BFS menjamin hop terpendek pertama kali. Setiap alamat dikunjungi sekali. Siklus berhenti secara alami.
Kenapa DELETE lalu INSERT per block?
Idempotency. Run ulang range yang sama menghasilkan baris identik. Granularitas block = rollback cepat saat reorg.
Kenapa klasifikasi contract lazy?
Kebanyakan alamat tidak muncul di query trace. Lazy = hanya klasifikasi saat diquery. Cache di tabel addresses.
Kenapa log_index = -1 untuk native ETH?
Transfer ETH bukan event, tidak punya log index. Pakai -1 supaya constraint UNIQUE (tx_hash, log_index) tetap valid dan membedakan ETH dari ERC-20.

6.0.1 Cara Problem Solving

Q: "Bagaimana kamu approach project ini dari awal?"

Pertama, saya baca requirements sampai habis. Yang diminta:
ingest, storage, trace, API, robustness. Saya breakdown jadi
layer-layer yang bisa dibangun secara incrementally.

Urutan saya:
1. Schema database — ini fondasi, harus benar dulu
2. Ingestion — ambil data dari RPC, simpan ke SQLite
3. Trace algorithm — BFS dengan temporal rule
4. API — expose trace lewat HTTP
5. Tests — verifikasi semua edge case
6. Verification — bandingkan dengan seed queries

Setiap layer saya test sebelum lanjut. Ini pola yang saya pakai
juga di KonaKorp: build kecil, test, verify, baru expand.

Q: "Saat menghadapi masalah, apa langkah pertama kamu?"

Define masalah secara spesifik. Bukan "tidak bisa jalan"
tapi "query ini return kosong untuk tx yang ada di DB".

Contoh nyata: awalnya trace mengembalikan edge yang seharusnya
tidak ada — transfer yang terjadi SEBELUM dana sampai ke alamat.

Saya isolasi: cek seed edges dulu, lalu BFS step-by-step,
lihat di hop mana edge salah muncul. Ketemu: temporal rule
hanya cek relatif ke seed, bukan per-hop.

Solusi: catat timestamp setiap kali alamat menerima dana,
edge berikutnya harus SETELAH timestamp itu.

Q: "Ceritakan situasi di mana kamu stuck, dan bagaimana keluar"

Stuck terbesar: reorg handling.

Awalnya saya tidak handle reorg sama sekali. Tapi pas ingest
live data dari Sepolia, ada block yang parentHash-nya tidak cocok.
Sistem crash karena assume chain selalu linear.

Saya baca dokumentasi Ethereum tentang reorg. Kemudian implement:
1. Setiap block, cek parentHash vs stored hash
2. Jika tidak cocok, walk backward ke common ancestor
3. Delete semua di atas ancestor (CASCADE)
4. Re-ingest dari sana

Butuh 3-4 iterasi sampai benar — termasuk handle kasus edge
di mana reorg terjadi setelah ingestion berhenti (verifyTail).

Q: "Bagaimana kamu memprioritaskan fitur?"

Saya pakai MoSCoW:

Must (harus jalan):
- Ingest data dari RPC ke SQLite
- Trace transaksi/alamat dengan BFS
- REST API untuk query
- Tests untuk trace dan ingestion

Should (penting untuk robustness):
- Reorg handling
- Idempotency (ingest 2x = hasil sama)
- Retry dengan backoff
- Follow mode (real-time)

Could (nice-to-have):
- Find-seeds tool
- Verification command
- Architecture documentation

Won't (untuk sekarang):
- Internal call tracing
- ERC-721/1155
- Caching layer
- Authentication

Yang "Must" harus jalan dulu sempurna. Baru tambah "Should".

6.1 Penjelasan Kode — Ditanya Langsung Soal Baris Kode

Q: "Apa yang terjadi kalau extractTransfers menerima ERC-721?"

ERC-721 Transfer punya 4 topik (signature, from, to, tokenId). Kita cek topics.length !== 3 → di-skip. Karena assment cuma minta ETH + ERC-20, ERC-721 tidak perlu ditangkap. Kalau mau tambah nanti, tinggal ubah filternya.

Q: "Kenapa amount disimpan sebagai string, bukan number?"

uint256 Ethereum bisa sampai 2^256. JavaScript Number hanya sampai 2^53. Kalau pakai number, ada precision loss. BigInt bisa, tapi SQLite tidak support BigInt. Jadi kita simpan sebagai string desimal: "1000000000000000000". Bisa dikonversi balik kapan saja.

Q: "Apa yang terjadi jika writeBlock gagal di tengah loop?"

Masuk catch block → ROLLBACK. Semua perubahan dibatalkan. Block yang belum selesai tidak masuk DB. Karena cursor tidak diupdate, run berikutnya akan resume dari block terakhir yang berhasil. Tidak ada partial write.

Q: "Bagaimana cara kerja topicToAddress?"

const topicToAddress = (t: string) => ('0x' + t.slice(-40)).toLowerCase();

Topic ERC-20 berformat 32 bytes (66 karakter hex termasuk 0x). 20 byte terakhir = alamat. slice(-40) ambil 40 karakter terakhir, tambah 0x di depan. Karena address EVM case-insensitive, toLowerCase() standarisasi.

Q: "Kenapa edgesFor mengambil limit + 1?"

out.push(...(stmt.all(a, lo, hi, perAddrLimit + 1) as Transfer[]));

Kita ambil 1 lebih banyak dari batas. Jika hasilnya perAddrLimit + 1 baris, berarti ada fan-out melebihi batas. Caller (BFS) bisa deteksi dan set truncated = true. Kalau ambil tepat limit, kita tidak tahu apakah masih ada data di belakangnya.

Q: "Apa bedanya INSERT OR REPLACE vs INSERT OR IGNORE di SQLite?"

  • INSERT OR REPLACE: Jika ada row dengan PRIMARY KEY/UNIQUE yang sama, HAPUS yang lama, INSERT yang baru. Dipakai untuk blocks karena hash bisa berubah (reorg).
  • INSERT OR IGNORE: Jika ada yang sama, DIAM saja. Dipakai untuk transfers dan addresses karena data yang sama = tidak perlu diupdate.

Q: "Bagaimana withRetry memutuskan kapan berhenti retry?"

6 percobaan. Jika semua gagal, throw error terakhir. Tapi isRangeTooLarge error langsung di-throw tanpa retry — karena itu bukan error sementara, tapi batasan provider. Jadi kita handle dengan span halving, bukan retry.

Q: "Apa yang dimaksud UNIQUE (tx_hash, log_index) di tabel transfers?"

Satu transaksi bisa punya banyak transfer (fan-out). Tapi setiap transfer unik dari kombinasi tx hash + log index. Untuk ETH native, log index = -1 (hanya 1 per tx). Untuk ERC-20, setiap event punya log index berbeda. Ini mencegah duplikasi jika ingest dijalankan 2x.

6.2 Blockchain Basics — Pastikan Paham Konsep

Q: "Apa itu Sepolia?"

Ethereum testnet. Dipakai untuk development/testing tanpa pakai uang sungguhan. Chain ID 11155111. Transaksi di sini tidak punya nilai moneter nyata.

Q: "Apa bedanya EOA dan Contract?"

  • EOA (Externally Owned Account): Punya private key, bisa initiate transaksi. Mulai dari 0x + 40 hex.
  • Contract: Punya kode yang dijalankan di EVM. Tidak punya private key. Dideploy lewat transaksi dengan to = null.

Di sistem ini, kita klasifikasi via eth_getCode: jika code = '0x' → EOA, selain itu → contract.

Q: "Apa itu ERC-20?"

Standar token di Ethereum. Contoh: USDC, DAI, WETH. Setiap transfer memancarkan event Transfer(address from, address to, uint256 amount). Event ini bisa dibaca dari logs transaksi. Kita filter pakai topic signature 0xddf252ad....

Q: "Apa itu reorg?"

Ketika node menemukan chain yang lebih panjang dari yang tersimpan, dia replace beberapa block terakhir. Block yang di-replace jadi orphan. Di Sepolia reorg jarang tapi mungkin. Sistem kita deteksi via parentHash yang tidak cocok.

Q: "Apa itu eth_getLogs?"

RPC method untuk query events (logs) dari blockchain. Kita pakai untuk ambil event Transfer ERC-20. Bisa filter berdasarkan block range dan topic. Public endpoint sering batasi range (misal max 2000 block). Makanya kita pakai chunk adaptif.

Q: "Apa bedanya value dan data di transaksi?"

  • value: Jumlah ETH yang ditransfer (dalam wei). Hanya relevan untuk native ETH transfer.
  • data: Payload ke smart contract. Untuk ERC-20 transfer, berisi encoded function call. Untuk event, data berisi parameter yang tidak di-index (amount).

Q: "Kenapa ada yang namanya 'hop'?"

Hop = jarak dalam rantai transfer. Jika A kirim ke B, lalu B kirim ke C, itu 2 hop dari A ke C. Sistem kita trace sampai depth tertentu (default 3 hop). Ini penting untuk melihat alur uang yang berpindah tangan beberapa kali.

6.3 TypeScript & Node.js

Q: "Kenapa pakai node:sqlite bukan library seperti better-sqlite3?"

Node 22+ sudah punya SQLite built-in via experimental API. Keuntungan: zero dependency, tidak perlu native build step. Trade-off: API-nya masih experimental, bisa berubah. Tapi untuk project ini cukup.

Q: "Apa itu DatabaseSync di node:sqlite?"

SQLite synchronous API di Node. Semua operasi DB jalan synchronously (tidak perlu await). Ini oke karena SQLite single-writer — tidak ada concurrent write yang perlu di-handle. Lebih simpel dari async API.

Q: "Kenapa pakai tsx bukan ts-node?"

tsx lebih cepat, tidak butuh tsconfig.json yang kompleks, dan support ES modules dengan baik. ts-node lebih tua, sering punya issue dengan "type": "module" di package.json.

Q: "Apa itu WAL mode di SQLite?"

Write-Ahead Logging. Mode di mana write tidak langsung lock database. Reader bisa baca sementara writer menulis. Cocok untuk我们的 use case: API (reader) jalan bersama ingester (writer). Tanpa WAL, ada lock contention.

Q: "Kenapa bigint tidak langsung disimpan ke SQLite?"

SQLite tidak punya tipe BigInt. node:sqlite juga tidak support BigInt langsung. Jadi kita konversi ke string: value.toString(). Untuk query, baca sebagai string lalu BigInt() jika perlu.

6.4 Scenario & Debugging

Q: "User bilang hasil trace-nya kosong untuk tx yang jelas ada. Apa yang kamu cek?"

  1. Cek apakah tx ada di window: curl localhost:3000/health — lihat window berapa
  2. Cek apakah tx punya transfer: query langsung ke DB atau pakai transfersByTx
  3. Cek apakah tx di luar window (block < 11672000 atau > 11673999)
  4. Cek apakah tx tidak punya value transfer (hanya contract interaction tanpa ETH)
  5. Cek apakah direction salah (user minta down tapi transfer masuk ke tx)

Q: "Ingest tiba-tiba lambat sekali. Diagnosa?"

  1. Cek log: apakah ada "getLogs span too large" berulang? Berarti provider rate-limit
  2. Cek apakah chunk size sudah turun ke 10 (minimum)
  3. Cek apakah RPC endpoint berubah (public endpoint sering throttled)
  4. Coba ganti SEPOLIA_RPC_URL ke Alchemy/Infura
  5. Cek network: mungkin ada masalah koneksi

Q: "Sistem bilang 'reorg detected' tapi kita tahu tidak ada reorg. Kenapa?"

Kemungkinan: RPC endpoint mengembalikan block yang sedikit berbeda (misal timestamp berbeda, atau ada fork minor). Atau: kita mengambil block dari RPC yang berbeda di fetch yang berbeda, dan ada perbedaan antara mereka. Solusi: pastikan konsisten pakai 1 RPC endpoint.

Q: "Bagaimana jika ada 2 transaksi di block yang sama, dari alamat yang sama, ke tujuan yang sama?"

Bedanya di txIndex dan logIndex. Sistem mengurutkan berdasarkan (block, txIndex, logIndex). Jadi meskipun from/to sama, mereka dianggap edge terpisah dengan urutan chronologis yang benar.

Q: "Apa yang terjadi jika trace mencapai batas maxNodes?"

Stop expansion. Return hasil parsial dengan truncated: true dan truncatedAt berisi alamat yang sedang di-explore. Sistem tidak pernah salah — hanya tidak lengkap. Client bisa tahu ada data lebih banyak.

Q: "Bagaimana jika alamat A mengirim ke B, lalu B langsung kirim ke A (dalam tx yang sama)?"

Karena seed berada di hop 0, A dan B sudah visited. Saat BFS mencoba expand B → A, A sudah ada di visited → skip. Siklus berhenti. Tapi edge B→A tetap ada di hasil (sebagai hop 1) karena edge ditambahkan sebelum cek visited.

6.5 Design Decisions — Kenapa Bukan Yang Lain

Q: "Kenapa tidak pakai graph database seperti Neo4j?"

Transfer graph cukup simpel: alamat → edge. BFS query natural dengan SQL index yang sudah ada. SQLite zero deployment. Neo4j overkill untuk use case ini. Kalau butuh complex graph traversal (centrality, community detection), baru Neo4j masuk akal.

Q: "Kenapa tidak pakai Postgres langsung?"

Assment bilang "justify your data model". SQLite paling sederhana untuk demo. Tidak butuh install service, tidak butuh config. Single file, langsung jalan. Kalau untuk production multi-user, baru Postgres.

Q: "Kenapa tidak pakai Redis untuk caching?"

Tidak ada di requirement. Sistem ini single-user, trace on-demand. Cache berguna jika ada banyak user query yang sama berulang kali. Tapi untuk demo, SQLite sudah cukup cepat.

Q: "Kenapa node:http bukan Express/Fastify?"

Hanya 1 runtime dependency (viem). node:http cukup untuk 4 route. Tidak perlu middleware, routing library, atau framework. Lebih simpel, lebih sedikit yang bisa rusak.

Q: "Kenapa from dan to di-lowercase?"

EVM address case-insensitive. 0xABC = 0xabc. Jika tidak standarisasi, bisa dianggap alamat berbeda. 0xABC...xyz dan 0xabc...xyz seharusnya 1 alamat yang sama. Lowercase menjamin konsistensi.

Q: "Bagaimana jika saya ingin trace transfer yang melibatkan 500 alamat?"

maxNodes default 500, maxEdgesPerNode default 200. Jika fan-out besar, truncated = true. Bisa naikkan limit: ?maxNodes=5000&maxEdgesPerNode=1000 (maks server). Tapi hati-hati: bisa lambat dan besar response-nya.

6.9 Pertanyaan Tricky / Gotcha

Q: "Jika A kirim 1 ETH ke B di block 100, lalu B kirim 0.5 ETH ke C di block 99, apakah C ter-trace?"

Tidak. Karena B menerima dana di block 100, tapi transfer B→C terjadi di block 99 (sebelum B punya dana). Aturan temporal per-hop menolak edge ini. C tidak akan muncul di downstream trace dari A.

Q: "Bagaimana jika satu tx memiliki 100 transfer ERC-20 dari 100 alamat berbeda?"

Semua 100 transfer masuk sebagai seed edges. BFS dimulai dari 100 alamat penerima sekaligus. Ini bisa trigger maxNodes limit. Sistem akan truncate dan beri tahu di truncatedAt.

Q: "Apa yang terjadi jika eth_getCode untuk alamat tidak ada?"

Viem akan return '0x' (empty code). Sistem kita interpret sebagai EOA. Jika RPC error, kita catch dan biarkan isContract tetap null. Tidak fatal — trace tetap jalan.

Q: "Bisakah trace mengembalikan jumlah hop yang salah?"

Tidak, jika aturan temporal diikuti. BFS menjamin shortest path. Tapi hops hanya menghitung directed path. Jika uang mengalir A→B→C tapi tidak ada edge langsung A→C, hops = 2. Jika ada edge A→C langsung, hops = 1 (karena BFS lebih cepat menemukan).

Q: "Apa yang terjadi jika ingest dijalankan 2x secara bersamaan?"

SQLite WAL mode handle concurrent reads, tapi single writer. Jika 2 ingester jalan bareng, yang kedua akan tunggu lock. Tapi karena DELETE-then-INSERT per block, hasil akhirnya sama (idempotent). Tapi tidak efisien — makanya README bilang "run one ingester at a time".

Q: "Kenapa getLogs pakai topic filter, bukan address filter?"

Kita ingin semua Transfer events di semua contract ERC-20, bukan dari 1 contract tertentu. Filter by topic = ambil semua Transfer dari semua token. Filter by address = hanya 1 token. Kita butuh semua.
