src/ingest.ts 181 lines

Purpose: Pull blocks from RPC, extract transfers, write to SQLite. Handle reorgs, retries, provider limits.

ingestRange flow

  1. Start with chunk size (default 200), clamped to [10, 2000]
  2. For each chunk:
    • rpc.getTransferLogs(n, end) — ERC-20 Transfer events
    • If "too many results" → halve chunk, retry
    • rpc.getBlock(b) for each block (parallelized, concurrency=8)
    • Check parentHash → detect reorg
    • If reorg: find common ancestor, rollback, restart
    • Otherwise: extractTransfers() → db.writeBlock()
  3. Log progress, double chunk size (up to ceiling)

extractTransfers

Two sources of transfers:

  1. Native ETH: tx.value > 0n && tx.to !== null → logIndex: -1, asset: 'ETH'
  2. ERC-20: topics.length === 3 && data.length === 66 → extract from/to from topics, amount from data
    • Filters out: 4-topic (ERC-721), short data (not uint256)

Reorg handling

Walk backward comparing stored hash to live hash. First match = common ancestor. Delete everything above, re-ingest.

verifyTail

For follow mode: check last 12 stored blocks each poll. If hash mismatch → rollback.

Types

type TraceOptions = {
  depth?: number;           // max hops (default 3)
  direction?: 'down' | 'up' | 'both';
  maxNodes?: number;        // default 500
  maxEdgesPerNode?: number; // default 200

};

  seed: { type: 'tx' | 'address'; value: string };
  window: [number, number];
  nodes: TraceNode[];       // { address, hop, isContract }
  edges: TraceEdge[];       // Transfer + { hop, direction }
  truncated: boolean;
  truncatedAt: string[];
};

traceTx

  1. Load seed edges via db.transfersByTx(txHash)
  2. Set seed position: (block, txIndex, -1)
  3. BFS downstream from recipients
  4. BFS upstream from senders
  5. finish(): build nodes, dedup edges

Temporal rule

const after = (e: Transfer, p: Pos) => cmp(e, p) > 0;
const before = (e: Transfer, p: Pos) => cmp(e, p) < 0;
const cmp = (e: Transfer, p: Pos) =>
  e.blockNumber - p.block || e.txIndex - p.txIndex || e.logIndex - p.logIndex;

Compares (block, txIndex, logIndex) tuples. Downstream must be strictly after; upstream strictly before.

Cycle termination

Each address visited once at shortest hop. BFS guarantees first visit = shortest.

Fan-out cap

if (edges.length > o.maxEdgesPerNode) {
  edges = edges.slice(0, o.maxEdgesPerNode);
  res.truncated = true;
  res.truncatedAt.push(addr);
}

4. Data Flow

Ingestion Flow

CLI (cli.ts) → assertSepolia() // verify chain ID → createChainReader() // viem client → ingestRange() // (ingest.ts) → for each chunk: rpc.getTransferLogs() // ERC-20 events rpc.getBlock() × N // block headers + txs for each block: check parentHash // reorg detection extractTransfers() db.writeBlock() → update cursor

Trace Query Flow

HTTP request (server.ts) → route() // parse URL + params → traceTx(db, hash, opts) // (trace.ts) → db.transfersByTx() // seed edges → bfs(db, ..., 'down') // downstream BFS → bfs(db, ..., 'up') // upstream BFS → finish() // build nodes, dedup edges → classify(db, rpc, result) // eth_getCode for unknowns → JSON response

Hops Query Flow

HTTP request (server.ts) → route() → hops(db, from, to, opts) // (trace.ts) → BFS from source → expand neighbors each hop → check temporal rule → return when destination reached or maxDepth hit → JSON response

5. Key Design Decisions

Why SQLite over Postgres?
Zero infrastructure — single file, comes with Node. Sufficient for single-user trace tool. WAL mode handles concurrent reads + single writer.
Why transfer-only edges?
Covers ETH + ERC-20 (the two required types). Internal calls would need debug_traceTransaction which public endpoints don't expose.
Why BFS not DFS?
BFS guarantees shortest hop first. Each address visited once. Cycles terminate naturally.
Why DELETE-then-INSERT per block?
Idempotency. Re-running same range converges to identical rows. Block granularity = fast rollback on reorg.
Why lazy contract classification?
Most addresses never appear in trace queries. Lazy = only classify when queried. Cache in addresses table.
Why log_index = -1 for native ETH?
ETH transfers don't have a log index. Using -1 keeps UNIQUE (tx_hash, log_index) valid and distinguishes ETH from ERC-20.

6.1 Code Walkthrough

Q: "Explain extractTransfers at src/ingest.ts:122"

export function extractTransfers(block: RpcBlock, logs: RpcLog[]): Transfer[] {
  const out: Transfer[] = [];
  // 1. Native ETH transfers
  for (const tx of block.transactions) {
    if (tx.value > 0n && tx.to) {    // skip contract creation (to=null)
      out.push({
        txHash: tx.hash,
        blockNumber: block.number,
        txIndex: tx.transactionIndex,
        logIndex: -1,                 // sentinel for native ETH
        from: tx.from.toLowerCase(),
        to: tx.to.toLowerCase(),
        asset: 'ETH',
        amount: tx.value.toString(),  // bigint → string for precision
      });
    }
  }
  // 2. ERC-20 Transfer events
  for (const l of logs) {
    if (l.topics.length !== 3 || l.data.length !== 66) continue;
    // topics[0] = event sig, topics[1] = from (indexed), topics[2] = to (indexed)
    // data = amount (non-indexed, uint256)
    out.push({
      txHash: l.transactionHash,
      blockNumber: l.blockNumber,
      txIndex: l.transactionIndex,
      logIndex: l.logIndex,
      from: topicToAddress(l.topics[1]),
      to: topicToAddress(l.topics[2]),
      asset: l.address.toLowerCase(),
      amount: BigInt(l.data).toString(),
    });
  }
  return out;
}
Why topics.length !== 3? ERC-20 has 3 topics; ERC-721 has 4. We filter out ERC-721.
Why data.length !== 66? 0x + 64 hex = 32 bytes = uint256.
Why logIndex = -1? ETH isn't an event. -1 keeps UNIQUE constraint valid.

Q: "Explain the BFS at src/trace.ts:124"

function bfs(db, res, visited, start, dir, o) {
  const side = dir === 'down' ? 'from' : 'to';
  let frontier = uniq(start);

  for (let hop = 1; hop <= o.depth && frontier.length > 0; hop++) {
    const next = new Set<string>();
    for (const addr of frontier) {
      const since = visited.get(addr)?.pos;
      let edges = db.edgesFor(side, [addr], o.window[0], o.window[1], o.maxEdgesPerNode);
      if (since) edges = edges.filter((e) => (dir === 'down' ? after(e, since) : before(e, since)));
      if (edges.length > o.maxEdgesPerNode) {
        edges = edges.slice(0, o.maxEdgesPerNode);
        res.truncated = true;
        res.truncatedAt.push(addr);
      }
      for (const e of edges) {
        res.edges.push({ ...e, hop, direction: dir });
        const other = dir === 'down' ? e.to : e.from;
        if (!visited.has(other)) {
          visited.set(other, { hop, pos: posOf(e) });
          next.add(other);
        } else if (next.has(other) && seen.pos && ...) {
          seen.pos = posOf(e);  // earlier arrival at same hop
        }
      }
      if (visited.size >= o.maxNodes) { res.truncated = true; return; }
    }
    frontier = [...next];
  }
}
Why BFS? Shortest hop guaranteed. One visit per address. No infinite loops.
Temporal rule per-hop: Prevents tracing money moved before funds arrived at that address.

Q: "Explain writeBlock at src/db.ts:77"

writeBlock(block: BlockRow, transfers: Transfer[]) {
  this.sql.exec('BEGIN');
  try {
    this.sql.prepare('DELETE FROM transfers WHERE block_number = ?').run(block.number);
    this.sql.prepare('INSERT OR REPLACE INTO blocks ...').run(...);
    for (const t of transfers) {
      this.sql.prepare('INSERT OR IGNORE INTO transfers ...').run(...);
      this.sql.prepare('INSERT OR IGNORE INTO addresses ...').run(...);
    }
    this.sql.prepare('INSERT INTO cursor ...').run(block.number);
    this.sql.exec('COMMIT');
  } catch (e) {
    this.sql.exec('ROLLBACK');
    throw e;
  }
}
DELETE then INSERT: Idempotency — same block twice = same result.
Transaction: Partial failure → ROLLBACK, database stays consistent.

6.2 System Design Questions

Q: "Why SQLite over Postgres?"

  • Zero config — no service to install, single file
  • ACID — WAL mode, transaction support
  • Sufficient — 280k rows, single user
  • Trade-off — single writer, but fine for this use case
  • If production — migrate to Postgres for concurrent writes

Q: "If scaling to mainnet, what changes?"

  1. Storage: SQLite → Postgres
  2. Ingestion: Parallel workers
  3. Caching: Redis for hot traces
  4. API: Rate limiting, pagination, WebSocket
  5. Monitoring: Metrics, logging, alerting
  6. Internal calls: debug_traceTransaction
  7. ERC-721/1155: Additional topic filters

Q: "What if RPC provider is down?"

  • withRetry: 6 attempts, exponential backoff
  • isRangeTooLarge: detect rate limit, halve span
  • getCursor: resume from last committed block
  • Worst case: throw error, user can switch SEPOLIA_RPC_URL
  • No data loss — idempotent

Q: "What are the bottlenecks?"

  1. RPC calls — getBlock per block, getTransferLogs per chunk
  2. SQLite writes — WAL helps, but single writer
  3. Trace BFS — query per address, slow with many edges
  4. Contract classification — eth_getCode per unknown address
Optimizations done: Adaptive chunk, parallel getBlock (8), lazy classification, composite indexes.

6.3 Algorithm Questions

Q: "Why temporal rule per-hop, not just relative to seed?"

Seed: A → B at block 100
B → C at block 110 (ok)
C → D at block 105 (BEFORE C received from B!)

If only checking relative to seed: block 105 > 100, D would be traced. But C didn't have the funds at block 105.

Per-hop rule: Each hop must be AFTER that address received funds.

Q: "How do you handle cycles?"

if (!visited.has(other)) {
  visited.set(other, { hop, pos: posOf(e) });
  next.add(other);
}

Each address visited once. BFS guarantees first visit = shortest. No infinite loops.

Q: "What's the complexity?"

  • Time: O(V + E), bounded by maxNodes × maxEdgesPerNode
  • Space: O(maxNodes) for visited + frontier

6.5 Behavioral Questions

Q: "What did you learn from this project?"

  • Blockchain data extraction needs reorg handling, idempotency
  • Public RPC endpoints have unpredictable rate limits
  • Temporal ordering is critical for "follow the money"
  • Simple data model (SQLite) can be sufficient for specific use cases
  • AI accelerates development, but human must verify and defend

Q: "How did you divide work with AI?"

  • Me: Ingestion, data model, trace algorithm — core logic
  • AI: API layer, tests, documentation — boilerplate
  • Jointly: AI drafted, I reviewed and approved
  • Key: I can explain every line even if AI wrote it

Q: "What are the weaknesses?"

  1. No internal call tracing (needs debug_traceTransaction)
  2. No ERC-721/1155 support
  3. SQLite single writer
  4. No caching layer
  5. No authentication
  6. Window-bounded
